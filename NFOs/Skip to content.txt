Systemarchitektur des autonomen Creative Operating Systems: NGOS-X, Synapse OS und GOS Genome v3–v6Die Paradigmenevolution automatisierter Medienproduktionssysteme vollzieht derzeit den Übergang von monolithischen Schnitt-Pipelines zu hochmodularen, echtzeitfähigen und autonomen Betriebssystemarchitekturen. Das generative Gesamtsystem aus NGOS-X, Synapse OS und dem Genome Operating System (GOS) auf Basis des WE.ED.IT OIDA Native Genome (v3–v6) repräsentiert eine neuartige Schichtenarchitektur. In dieser Architektur verschmelzen deterministische Editier- und Montagemodelle mit generativen neuronalen Rekonstruktionseinheiten, einem autonomen Multi-Agenten-Regierat und echtzeitfähigen Audio-Synthese-Engines.Architektur-Überblick und evolutionäre SystemmetamorphoseDie Entwicklungsgeschichte des WE.ED.IT OIDA Native Genoms dokumentiert den systematischen Wandel von einer statischen Skriptsammlung zu einer vollständig autonomen, adaptiven Kernel-Architektur. Das Gesamtsystem ist strikt in Schichten unterteilt. An unterster Stelle steht der NGOS-X Microkernel, welcher die Hardware-Abstraktion, die Speicherisolierung und die unterbrechungsfreie Prozesskommunikation sicherstellt. Darüber agiert Synapse OS als semantischer Hypervisor zur Verwaltung von Rechenressourcen auf heterogenen GPU-, NPU- und DSP-Clustern. Das Genome Operating System (GOS) bildet die logische Laufzeitumgebung für kreative Regieanweisungen, visuelle Integritätsprüfungen und interoperative Timeline-Backend-Prozesse.Die Schichtenarchitektur gliedert sich vertikal von den tiefen Kernel-Ebenen bis zur Anwendungsschicht:System-Kernel-Schicht: Der NGOS-X Microkernel stellt capability-basierte Sicherheit, Zero-Copy-Interprozesskommunikation (IPC) und Threads-Scheduling für hardwarenahe Operationen bereit.Orchestrierungs-Schicht: Synapse OS abstrahiert die physikalische Hardwareinfrastruktur und verteilt generative Rechengraphen dynamisch auf zur Verfügung stehende Beschleunigerkerne.Audio-Visuelle Synthese- & Feedback-Schicht: SYNAPSE AUDIO DYNAM2CS steuert die prozedurale Audiosynthese, während Reflexive Creative Dynamics (RCD) eine geschlossene Feedback-Schleife zwischen Audio- und Vektordynamik aufrechterhält.Redaktions- & Backend-Schicht: Die OpenTimelineIO (OTIO) Core Engine verarbeitet Schnittstrukturen nativ in C++ und stellt Python-Schnittstellen für die automatisierte Timeline-Optimierung zur Verfügung.GOS-Laufzeitschicht: Das Genome Operating System orchestriert den Package Manager (weed install), den Genome Search Engine Index und die Constraint-Validierung.Kreative Steuerungsschicht: Der Multi Director Council evaluiert über Director Scripts fortlaufend Regie-Entscheidungen, generiert Replay-Protokolle und stellt Telemetrie-Dashboards via HTML Reporting bereit.Die nachfolgende Matrix verdeutlicht die evolutionäre Metamorphose der Genome-Iterationen AbstraktionDer NGOS-X Microkernel wendet das Microkernel-Architekturmuster konsequent auf die Anforderungen hochdimensionaler Medienverarbeitung an. Im Gegensatz zu monolithischen Schnittsystemen verlagert NGOS-X komplexe Systemdienste aus dem Systemkern in den geschützten Benutzerraum (User Space). Der Kernel beschränkt sich auf das Management essenzieller Grundfunktionen: Thread-Scheduling für heterogene Rechenknoten, präzise Speicherallokation und capability-basierte Interprozesskommunikation.Capability-basierte ProzessisolationInnerhalb von GOS laufen sämtliche Subsysteme – darunter die Neural-Rendering-Pipeline, der Video-Linter und die OpenTimelineIO-Parser-Instanzen – als voneinander isolierte User-Space-Prozesse. Die Zugriffskontrolle erfolgt über strikt definierte Capabilities. Ein Prozess für die Analyse visueller Constraints erhält beispielsweise reine Leserechte auf die im Speicher liegende OTIO-Struktur, kann jedoch keine Schreiboperationen auf GPU-Puffer durchführen. Diese Isolation schützt den Gesamtablauf: Der unvorhergesehene Absturz eines neuronalen Diffusionsmodells beeinträchtigt nicht die Integrität der Schnitt-Engine.Zero-Copy IPC & Shared Memory Ring BufferUm den immensen Datendurchsatz hochauflösender Videoframes und neuronaler Tensor-Buffer ohne Performance-Einbußen zwischen Analyse-, Render- und Optimierungs-Diensten zu übertragen, nutzt der NGOS-X Microkernel ein Zero-Copy-IPC-Verfahren. Der Datenaustausch erfolgt über im Microkernel registrierte Shared-Memory-Ringe. Der Puffer-Verbund $\mathcal{B}_{\text{shared}}$ wird mathematisch wie folgt beschrieben:$$\mathcal{B}_{\text{shared}} = \left\{ f_1, f_2, \dots, f_n \right\}, \quad f_i \in \mathbb{R}^{H \times W \times C}$$Hierbei repräsentieren $H$, $W$ und $C$ die Höhe, Breite und Kanalanzahl des Frame-Tensors $f_i$. Statt Bilddaten physisch im Hauptspeicher zu kopieren, übermittelt der Microkernel lediglich Capabilities-Referenzen auf die entsprechenden Speichersegmente, was Latenzzeiten auf Sub-Mikroskunden-Niveau reduziert.Synapse OS agiert als Hypervisor direkt auf dem NGOS-X Microkernel. Es analysiert die Auslastung der Hardware-Ressourcen in Echtzeit und übersetzt die abstrakten Ausführungsgraphen des GOS dynamisch in optimale Befehlsketten für Grafikkarten, Tensor-Einheiten und digitale Signalprozessoren.Das Genome Operating System (GOS) & Das Universal Asset Format (UAF)Das Genome Operating System (GOS) bildet die funktionale Ausführungsschicht oberhalb des Kernels. Es abstrahiert physikalische Speicherdaten, generative Prompts und Bearbeitungsschritte in ein objektorientiertes und konsistentes Datenmodell.Das Universal Asset Format (UAF)Ein zentraler Bestandteil des GOS ist das Universal Asset Format (UAF). UAF löst die Beschränkungen proprietärer Containerformate auf, indem es binäre Mediendaten, generative Parameter, Bewegungsvektoren und semantische Metadaten in einer einheitlichen Objektstruktur zusammenfasst. Die formale Definition eines UAF-Knotens $\mathcal{A}$ lautet:$$\mathcal{A} = \Big\langle \mathbf{M}_{\text{raw}}, \, \mathbf{E}_{\text{latent}}, \, \mathbf{S}_{\text{graph}}, \, \mathbf{P}_{\text{history}} \Big\rangle$$Die einzelnen Komponenten sind dabei wie folgt definiert:$\mathbf{M}_{\text{raw}}$ enthält die direkte binäre Referenz oder den Zeiger auf das physische Rohmaterial (Audio-, Video- oder Vektordaten).$\mathbf{E}_{\text{latent}}$ speichert hochdimensionale latente Vektoreinbettungen (z. B. CLIP- oder CLAP-Embeddings) zur Ähnlichkeitsbestimmung.$\mathbf{S}_{\text{graph}}$ beschreibt den räumlichen und zeitlichen Beziehungs-Graph zu allen verknüpften Assets innerhalb des Projekts.$\mathbf{P}_{\text{history}}$ dokumentiert den deterministischen Generierungspfad einschließlich verwendeter Random-Seeds, Prompts und Modell-Metadaten.Genome Search Engine Index (GSEI)Der Genome Search Engine Index (GSEI) ist eine in GOS integrierte Vektordatenbank, die sämtliche verfügbaren UAF-Knoten kontinuierlich im Hintergrund indiziert. Anstelle klassischer textbasierter Dateisuchen nutzt GSEI die Ähnlichkeit von Vektoreinbettungen im latenten Raum. Die Ähnlichkeit zwischen einer Regie-Suchanfrage $\vec{q}$ und einem Asset-Vektor $\vec{v}$ wird über die Kosinus-Ähnlichkeit errechnet:$$\text{Sim}(\vec{q}, \vec{v}) = \frac{\vec{q} \cdot \vec{v}}{\Vert{}\vec{q}\Vert{} \Vert{}\vec{v}\Vert{}}$$Dieser Mechanismus ermöglicht es dem System, innerhalb von Millisekunden ästhetisch, thematisch oder tonal passende B-Roll-Sequenzen, Übergänge und Klangeffekte aus riesigen Asset-Bibliotheken herauszufiltern.Das Package-Ökosystem & Package Manager (weed install)Zur dynamischen Erweiterung ästhetischer und technischer Fähigkeiten besitzt GOS ein modulares Paketverwaltungssystem, welches über den hauseigenen Package Manager weed install gesteuert wird. Analog zu modernen Software-Paketmanagern löst weed Abhängigkeiten zwischen Stil-Vorgaben, Kamerasystemen und Übergangsroutinen auf.Typologie der Package-Formate und SpezifikationenDas weed-Ökosystem unterteilt sich in vier primäre Paketkategorien, die jeweils spezifische Schnittstellen innerhalb von GOS ansprechen und durch eigene Validierungsroutinen abgesichert werden:Style Packages (weed-style): Enthalten feinjustierte Adapter-Gewichte (z. B. LoRA-Toren), dreidimensionale Farbkorrektur-Matrizen (3D LUTs) und Stil-Prompts für generative Bild- und Video-Pipelines.Camera Packages (weed-camera): Definieren mathematische Bezier-Splines für Kamera-Trajektorien, Brennweitenverläufe, Tiefenschärfe-Profile und Bewegungsmuster für synthetische Render-Kameras.Transition Packages (weed-transition): Reichen von klassischen Geometrie-Blenden bis hin zu latenten Morphing-Algorithmen, die zwei aufeinanderfolgende Videoclips über latente Interpolation nahtlos verschmelzen.Director Packages (weed-director): Beinhalten domänenspezifische Regie-Skripte, Bewertungs-Matrizen für automatische Schnitte und spezifische Regel-Sets für den Regierat.Package-KategorieInhaltskomponentenPrimäre GOS-SchnittstelleValidierungs-Mechanismusweed-styleLoRA-Tensor-Gewichte, Prompt-Templates, Color LUTsNeural Rendering PipelineLatente Vektor-Abstands-Prüfungweed-cameraSpline-Pfade, FOV-Skripte, Shake-Frequenz-ProfileVirtual Camera EngineKinematische Kollisions- & Smoothness-Prüfungweed-transitionCustom Shaders, Latent Morph Graphs, OTIO TransitionsOpenTimelineIO Schnitt-EngineFrame-Overlap- Check & Buffer-Validierungweed-directorRegie-Skripte, Bewertungs-Matrizen, Constraint SetsMulti Director CouncilKonsens-Test (Monte-Carlo-Simulation)Der Befehl weed install weed-style-cyberpunk lädt das angeforderte Paket herunter, prüft dessen Kompatibilität mit der aktiven Genome-Version, registriert die enthaltenen Vektoren im Genome Search Engine Index und stellt die neuen Stilmuster dem autonomen Entscheidungsrat zur Verfügung.Autonomous Direction & Multi Director CouncilDie ästhetische und narrative Ausgestaltung eines Medienprojekts erfolgt in GOS nicht über starre Vorlagen, sondern durch das Zusammenwirken eines autonomen Agentensystems: dem Multi Director Council.Director ScriptsEin Director Script formuliert die künstlerische Absicht eines Projekts in einer domänenspezifischen Sprache (DSL). Anstatt feste Frame-Nummern vorzugeben, definiert das Skript dynamische Zielkorridore für Tempo, Stimmungsbögen, Helligkeitsverteilungen und Schnittfrequenzen. Ein Director Script spezifiziert beispielsweise Zielwerte wie eine dynamische Beschleunigung des Schnitttempos von 60 auf 140 Schläge pro Minute sowie komplementäre Farbharmonien innerhalb definierter Toleranzgrenzen.Der Multi Director Council Konsens-MechanismusDer Multi Director Council setzt sich aus spezialisierten Software-Agenten zusammen, die unterschiedliche Gewerke der Filmproduktion repräsentieren:Cinematographer Agent: Evaluierte Bildeinstellungsgrößen, Kameraführung, Lichtstimmung und visuelle Balance.Editorial Agent: Optimiert das Schnitttempo, den rhythmischen Fluss und die narrative Kontinuität.Colorist Agent: Überwacht die chromatisches Kohärenz, den Kontrastumfang und die Einhaltung von Farbräumen.Sound Design Agent: Steuert die auditive Dynamik, Frequenzraumverteilungen und die Platzierung von Klangeffekten.Für jeden potenziellen Schnittkandidaten $\mathcal{C}$ berechnet der Rat eine gewichtete Gesamtnutzwert-Funktion $U_{\text{council}}$:$$U_{\text{council}} = \sum_{k \in \{\text{Cine}, \text{Edit}, \text{Color}, \text{Sound}\}} w_k \cdot S_k(\mathcal{C})$$Hierbei bezeichnet $S_k(\mathcal{C})$ den durch den Agenten $k$ vergebenen Score und $w_k$ die projektspezifische Gewichtung dieses Gewerks. Treten Zielkonflikte zwischen den Agenten auf – etwa wenn der Editorial Agent einen harten Schnitt fordert, der Colorist Agent jedoch vor einem zu starken Farbsprung warnt –, greift ein Konsensalgorithmus auf Basis einer Kreativ-Vektor-Befehlskette, um die historisch vielversprechendste Option auszuwählen.Visual Constraints EngineDie Visual Constraints Engine fungiert als unbestechliche Kontrollinstanz. Während der Multi Director Council gestalterische Freiheiten nutzt, setzt die Constraints Engine fundamentale kinematografische und technische Regeln durch. Sie verhindert typische handwerkliche Fehler wie:Blickachsen-Sprünge durch Verletzung der 180-Grad-Regel.Jump Cuts durch unzureichende Änderung der Einstellungsgröße oder des Kamerawinkels zwischen aufeinanderfolgenden Clips.Abrupte Farbraumsprünge und Signal-Clipping in extremen Helligkeitsbereichen.Sobald eine vom Regierat vorgeschlagene Schnittvariante eine harte Regel der Constraints Engine verletzt, wird die Option verworfen und der Rat gezwungen, eine alternative Lösung zu berechnen.Timeline Engine, Optimization & Quality AssuranceAls grundlegendes Datenmodell für die zeitliche Anordnung aller Medienelemente nutzt GOS den Open-Source-Standard OpenTimelineIO (OTIO), der unter dem Dach der Academy Software Foundation (ASWF) entwickelt wird. OTIO dient als herstellerunabhängiges In-Memory-Modell zur Repräsentation komplexer Schnittentscheidungen.OpenTimelineIO (OTIO) Native BackendsGOS nutzt OTIO nicht als simples Import-/Export-Format, sondern als primäre Datenstruktur im Arbeitsspeicher. Die Hierarchie baut auf standardisierten OTIO-Schema-Klassen auf:otio.schema.Timeline: Die Wurzelkomponente, welche die globale Startzeit (global_start_time) und den zentralen Spuren-Stapel (tracks) verwaltet.otio.schema.Stack: Ein Behälterobjekt zur parallelen Anordnung mehrerer Spuren für Video-, Audio- und Effektdaten.otio.schema.Track: Eine sequenzielle Abfolge von Medienclips (Clip), Übergängen (Transition) und zeitlichen Lücken (Gap).otio.schema.Clip: Repräsentiert die zeitliche Position eines Eintrags und verweist über seine media_reference auf das physikalische oder generierte Material.Im GOS-Backend unterscheidet die media_reference eines Clips zwischen zwei wesentlichen Zuständen: Existierende Medien werden über ExternalReference eingebunden, während noch zu generierende visuelle Elemente als MissingReference markiert sind. Dies signalisiert dem Render-Subsystem, dass ein generativer Job angestoßen werden muss. Für maximale Performance greift GOS direkt auf die C++-Core-Bibliothek von OTIO (src/opentimelineio) zu, wodurch Manipulationen der Timeline im Shared Memory des NGOS-X Microkernels ohne Overhead erfolgen. Python-Bindings (src/py-opentimelineio) werden ergänzend für High-Level-Agenten-Skripte genutzt.Schema-Versionierung & AbwärtskompatibilitätUm eine langfristige Kompatibilität bei Systemupdates zu gewährleisten, nutzt GOS das OTIO-Versionierungssystem. Jedes serialisierte Objekt besitzt ein schema_name- und ein schema_version-Feld. Wird eine ältere Projektdatei (z. B. aus Genome v4) in ein neueres GOS-System (Genome v6) geladen, transformiert die OTIO-Pipeline das Datenmodell über hinterlegte Upgrade-Funktionen schrittweise auf die aktuelle Schema-Version. Die Steuerung dieser Prozesse erfolgt über sogenannte Version Maps (CORE_VERSION_MAP) und Konfigurationsmanifeste (OTIO_PLUGIN_MANIFEST_PATH), wodurch eine vollständige Abwärts- und Aufwärtskompatibilität gewahrt bleibt.Timeline Optimizer & Video LinterDer Timeline Optimizer analysiert das OTIO-Graphmodell fortlaufend auf mathematische Redundanzen, verwaiste Spuren und zeitliche Überschneidungen. Über das Untermodul otio.opentime führt er framegenaue Arithmetik auf Basis von RationalTime-Objekten durch, was zeitliche Rundungsfehler bei gemischten Frame-Rates wirksam unterbindet.Der Video Linter führt eine automatisierte Qualitätssicherung vor dem Auslösen des Rendering-Prozesses durch. Seine Hauptaufgaben umfassen:Media Linker Verification: Überprüft, ob sämtliche MissingReference-Objekte durch gültige Dateipfade oder generierte Tensorspeicher ersetzt wurden.Temporal Gap Check: Identifiziert ungewollte 1-Frame-Lücken zwischen benachbarten Clips.Artifact Inspection: Scannt generierte Bildströme auf Inferenz-Abbrüche, Render-Artefakte und unvollständige Frames.Beat Sync Validation: Kontrolliert die zeitliche Ausrichtung visueller Schnittkanten an den auditiven Peak-Markern der Audiospuren.Synthetische Audiosteuerung & Reflexive Creative Dynamics (SYNAPSE AUDIO DYNAM2CS & RCD)Medienproduktion ist ein multimodaler Prozess, weshalb GOS die visuelle Schnitt-Engine direkt mit dem synthetischen Audiosystem SYNAPSE AUDIO DYNAM2CS koppelt.SYNAPSE AUDIO DYNAM2CSDYNAM2CS ist eine echtzeitfähige, prozedurale Audio-Synthese-Engine. Anstatt vorgefertigte Tonspuren zu laden, generiert DYNAM2CS dynamische Audio-Stems für Dialoge, Soundeffekte (SFX), Foleys und Musik-Atmosphären in Abhängigkeit von den visuellen Ereignissen.Das System nutzt dynamische Sidechaining-Prozesse im Frequenzraum. Steigt beispielsweise die visuelle Komplexität oder die Bewegungsdichte in einer Videosequenz, senkt DYNAM2CS automatisch mittenfrequente Anteile der Hintergrundmusik ab und hebt synchrone Transienten der SFX-Spur an, um die wahrgenommene Dynamik zu verstärken.Reflexive Creative Dynamics (RCD)Reflexive Creative Dynamics (RCD) stellt eine geschlossene Feedback-Schleife (Closed-Loop System) zwischen Bild- und Audioebene dar. Während des Schnittprozesses analysiert RCD fortlaufend das Wechselspiel beider Modalitäten:Visueller Impuls: Der Schnitt-Agent setzt einen neuen Cut in der OTIO-Timeline.Impuls-Berechnung: RCD berechnet den visuellen Änderungsvektor $I_v$:$$I_v = \frac{\Delta \text{Visuelle Komplexität}}{\Delta t}$$Auditiver Reflex: DYNAM2CS empfängt $I_v$ und passt die spektrale Verteilung sowie die Lautstärkenhüllkurve des Audiosignals innerhalb von unter $0.5 \, \text{ms}$ an.Resonanz-Evaluierung: RCD bewertet die verbleibende multimodale Dissonanz. Ergibt die Analyse eine Asynchronität zwischen visuellem und auditivem Eindruck, verschiebt RCD die In- und Out-Points des betroffenen Videoclips in der OTIO-Spur um wenige Frames, bis maximale Kohärenz erreicht ist.Auditierung, Director Replay & HTML ReportingUm vollautonome Entscheidungsabläufe transparent und reproduzierbar zu machen, besitzt GOS ein integriertes Telemetrie- und Replay-Subsystem.Director Replay SystemSämtliche Beschlüsse des Multi Director Councils, Fehlermeldungen der Visual Constraints Engine und Optimierungsschritte des Timeline Optimizers werden deterministisch im Director Replay Log aufgezeichnet. Da alle Entscheidungsprozesse auf definierten Zufallssämlingen (Seeds) und Zustandstransformationen basieren, erlaubt das Director Replay System die exakte, framegenaue Rekonstruktion des gesamten Entstehungsprozesses. Entwickler und Supervisoren können an jeden beliebigen Punkt der Projekt-Historie zurückspringen, die Argumentation einzelner Agenten analysieren und bei Bedarf manuell korrigierend eingreifen (Human-in-the-Loop).HTML Reporting EngineNach Abschluss eines Bearbeitungsschritts generiert GOS automatisch ein interaktives HTML-Telemetrie-Dashboard. Dieses Dashboard dient als zentrales Prüfwerkzeug für technische und künstlerische Abnahmen.Dashboard-ModulAnalysierte ParameterVerwendungszweckCouncil Decision MatrixAgenten-Votes, Nutzwert $U_{\text{council}}$, Konsens-StatusNachvollziehbarkeit künstlerischer SchnittentscheidungenOTIO Graph ViewerTrack-Struktur, Clips, Gaps, Transition-LängenInteraktive Inspektion der zeitlichen DatenstrukturLinter DiagnosticsMissingReference-Pfade, Frame-Drops, FarbraumsprüngeTechnische Qualitätssicherung und Render-FreigabeRCD Coherence PlotImpuls-Verlauf $I_v$, Audio-Frequency-CoverageAnalyse der audiovisuellen Synchronität und DynamikDas Reporting-Dashboard bündelt die Protokolle übersichtlich und ermöglicht es, kritische Schnittstellen oder fehlende Medienreferenzen (MissingReference) vor dem Rendering zu korrigieren.System-Synthese und AusblickDas autonome Creative Operating System auf Basis von NGOS-X, Synapse OS und GOS stellt eine fundamentale Neuausrichtung digitaler Medienproduktionsarchitekturen dar. Durch die klare Trennung von Hardware-Abstraktion im NGOS-X Microkernel, semantischer Prozess-Orchestrierung in Synapse OS, herstellerunabhängiger Schnittdatenverwaltung via OpenTimelineIO und kinematischer Agentensteuerung im GOS wird ein Höchstmaß an Modularität, Ausfallsicherheit und Leistungsfähigkeit erzielt.Die Entkopplung des Universal Asset Formats (UAF) von proprietären Software-Editoren sowie die Einführung eines dedizierten Paket-Ökosystems über weed install gewährleisten, dass sich das System flexibel an neue generative Modelle und Schnitttechniken anpassen lässt. Künftige Iterationen der Genome-Architektur (v7+) werden die Grenzen zwischen Rendering, Audiosynthese und Schnitt weiter auflösen, indem neuronale Vektorräume direkt im nativen Shared Memory des Kernels verarbeitet werden. GOS etabliert damit einen praxistauglichen Standard für die autonome und nachvollziehbare Medienproduktion der Zukunft.

oefoef — Beat-Sync Video Engine
SYNAPSE AUDIO DYNAMICS & WE.ED.IT-Core: eine autonome, offline-first Pipeline, die aus MP3s und einem lokalen Clip-Pool automatisch musiksynchrone Videos samt Upload-Strategie generiert. Dieses Dokument beschreibt das komplette Repository — nicht nur main.py, sondern alle Module, die die Pipeline tragen.

Wurzel: J:\Oidasheim\oefoef
Python: 3.10+ (getestet auf 3.12)
Status: End-to-End verifiziert (siehe UPGRADE.md, 2026-08-31)
Überblick
Was dieses Repository ist — und was es nicht ist.

Der Kern des Repos ist eine schlanke, deterministische Pipeline aus rund 15 zusammenspielenden Python-Modulen (Einstieg: main.py). Sie analysiert Songs und Videoclips rein lokal, baut daraus eine musiksynchrone Schnitt-Timeline und rendert per direktem ffmpeg-Subprocess ein fertiges Video — inklusive lernendem Feedback-Loop, semantischer Song/Clip-Zuordnung und automatisch generierter Upload-Strategie.

Daneben enthält der Ordner sehr viel Drumherum: Backups älterer main.py-Stände, experimentelle Einzelskripte (Lyrics-/Punchline-Generatoren, Songrid-Tools, ein optionales Unreal-Engine-Renderbackend, ein Schwesterprojekt "WONG"), große Datenexporte sowie mehrere gepackte Archive. Dieses Handbuch trennt bewusst Kern, optional/experimentell und Legacy/Sonstiges.

Einstiegspunkt
main.py — 1-Click Batch- oder Einzelsong-Verarbeitung.

Persistenz
SQLite (beat_sync.db) + JSON-Cache (libsync-flat-globe.db.json).

Rendering
ffmpeg-Subprocess (Standard) oder optional Unreal Engine Movie Render Queue.

Weitere CLIs
song_semantics.py (Lyrics-Lerner) und viral-strategy.py (Release-Planer) sind eigenständig aufrufbar.

timeline_builder.py
641 Zeilen
Kernstück der Clip-Auswahl. Baut aus Song-Analyse + Tag-Vektor + Clip-Globe eine frame-genaue Schnittliste. Score pro Kandidat-Clip:

score = SEMANTIC_WEIGHT * cosine(song_vec, clip_vec)
      + (1-SEMANTIC_WEIGHT) * energy_match(section_label, clip.motion_score)
      + FACE_BOOST_VOCAL (falls Sektion vokal/emotional UND face_score hoch)
Anti-Repeat kombiniert drei Ebenen: NO_REPEAT_WINDOW (harte Sperre innerhalb des aktuellen Renders), PARTIAL_REPEAT_COOLDOWN_SEC (zeitbasiert, rendersübergreifend über beat_sync.db) und MAX_CLIP_USES_TOTAL (harte Obergrenze über die gesamte Historie). Gesperrt wird dabei nur der tatsächlich genutzte Zeitbereich eines Clips, nicht der ganze Clip.

build_timeline() — Haupteinstieg, von main.py::process_song aufgerufen.
_pick_clip() — Kandidaten-Scoring + Auswahl pro Segment.
_resolve_oida_semantics() — songspezifische Struktur-/Semantik-Auflösung.
_apply_structure_tempo() / _polyrhythm_jitter() — Tempo-/Rhythmus-Feinjustierung.
_maybe_extend_for_breath() — Segment-Verlängerung in ruhigen Passagen.

Rendering
Vom EDL zum fertigen MP4 — ohne moviepy/ffmpeg-python-Wrapper, direkt per Subprocess.

renderer.py
1148 Zeilen
Extrahiert pro Segment einen Clip, wendet eine virtuelle Kamera an (Pan/Zoom), normalisiert auf gleiche Auflösung/FPS, konkateniert per concat-Demuxer (frame-genau, kein Re-Encode-Drift) und legt am Ende die Original-MP3 als Tonspur über die gesamte Länge.

Virtuelle Kamera: Zoom nur wenn er etwas bringt — Seitenverhältnis-Mismatch erzwingt Zoom-Fill; segment.camera steuert push (langsamer Ken-Burns-Zoom), snap (schneller Punch-In), drift (Zoom + seitliches Pan) oder hold (meist statisch). Pan-Richtung leitet sich primär aus der tatsächlich erkannten Bewegungsrichtung des Clips ab (clip_pool.motion_direction), mit deterministischem Hash-Seed als Fallback. Für push/drift kommt zusätzlich ein dezenter, animierter Keystone/Perspective-Shift für Pseudo-3D-Tiefe dazu.

render_music_video() — Haupteinstieg (identische Signatur wie unreal_renderer).
_plan_camera() / _zoompan_filter() / _perspective_filter() — Kamera-Logik.
_build_push_fade_transition() / _build_scratch_transition() — Übergangs-Rendering.
_nvenc_available() — nutzt Hardware-Encoding (NVENC), wenn verfügbar.
_write_ffmetadata_file() — bettet MP4-Tags/Kapitel aus main.py-Metadata ein.

Bekannte Lücken & Diskrepanzen
Stellen, an denen Code-Kommentare/Docstrings mehr versprechen, als main.py aktuell tatsächlich tut.

clip_tagging.py ist nicht verdrahtet: Weder der Import noch ein Aufruf von tag_clips_after_render() tauchen in main.py auf. Die im Code dokumentierte Kette "main.py::process_song → tag_clips_after_render()" existiert nicht (mehr) — Original-Clip-Dateien bekommen aktuell keine Nutzungs-Metadaten in die MP4-Tags geschrieben.
--mp3-root und --no-clip-tags fehlen im Parser: Kommentare in config.py und in main.py selbst (Zeile ~848) sprechen von einem geplanten --mp3-root-Flag (mehrfach angebbar) bzw. einem --no-clip-tags-Schalter. Im aktuellen argparse-Setup von main.py existiert keiner der beiden — nur config.MP3_ROOTS (per Env-Variable) steuert die Song-Quelle.
Viele Root-Skripte sind unabhängig von main.py: Dateien wie oida_track_generator_v5.py, oidaheim_archive_miner_v2_420_weed_beats.py, canvas-export.py oder die agents/-Skripte werden von der Kern-Pipeline nicht importiert. Sie sind eigenständige Experimente/Tools desselben Projektkontexts, aber kein Teil des python main.py-Laufs.

Überblick

Was dieses Repository ist — und was es nicht ist.

Der Kern des Repos ist eine schlanke, deterministische Pipeline aus rund 15 zusammenspielenden Python-Modulen (Einstieg: main.py). Sie analysiert Songs und Videoclips rein lokal, baut daraus eine musiksynchrone Schnitt-Timeline und rendert per direktem ffmpeg-Subprocess ein fertiges Video — inklusive lernendem Feedback-Loop, semantischer Song/Clip-Zuordnung und automatisch generierter Upload-Strategie.

Daneben enthält der Ordner sehr viel Drumherum: Backups älterer main.py-Stände, experimentelle Einzelskripte (Lyrics-/Punchline-Generatoren, Songrid-Tools, ein optionales Unreal-Engine-Renderbackend, ein Schwesterprojekt "WONG"), große Datenexporte sowie mehrere gepackte Archive. Dieses Handbuch trennt bewusst Kern, optional/experimentell und Legacy/Sonstiges.

Einstiegspunkt

main.py — 1-Click Batch- oder Einzelsong-Verarbeitung.

Persistenz

SQLite (beat_sync.db) + JSON-Cache (libsync-flat-globe.db.json).

Rendering

ffmpeg-Subprocess (Standard) oder optional Unreal Engine Movie Render Queue.

Weitere CLIs

song_semantics.py (Lyrics-Lerner) und viral-strategy.py (Release-Planer) sind eigenständig aufrufbar.

timeline_builder.py641 Zeilen

Kernstück der Clip-Auswahl. Baut aus Song-Analyse + Tag-Vektor + Clip-Globe eine frame-genaue Schnittliste. Score pro Kandidat-Clip:

score = SEMANTIC_WEIGHT * cosine(song_vec, clip_vec)
      + (1-SEMANTIC_WEIGHT) * energy_match(section_label, clip.motion_score)
      + FACE_BOOST_VOCAL (falls Sektion vokal/emotional UND face_score hoch)

Anti-Repeat kombiniert drei Ebenen: NO_REPEAT_WINDOW (harte Sperre innerhalb des aktuellen Renders), PARTIAL_REPEAT_COOLDOWN_SEC (zeitbasiert, rendersübergreifend über beat_sync.db) und MAX_CLIP_USES_TOTAL (harte Obergrenze über die gesamte Historie). Rendering

Vom EDL zum fertigen MP4 — ohne moviepy/ffmpeg-python-Wrapper, direkt per Subprocess.

renderer.py1148 Zeilen

Extrahiert pro Segment einen Clip, wendet eine virtuelle Kamera an (Pan/Zoom), normalisiert auf gleiche Auflösung/FPS, konkateniert per concat-Demuxer (frame-genau, kein Re-Encode-Drift) und legt am Ende die Original-MP3 als Tonspur über die gesamte Länge.

Virtuelle Kamera: Zoom nur wenn er etwas bringt — Seitenverhältnis-Mismatch erzwingt Zoom-Fill; segment.camera steuert push (langsamer Ken-Burns-Zoom), snap (schneller Punch-In), drift (Zoom + seitliches Pan) oder hold (meist statisch). Pan-Richtung leitet sich primär aus der tatsächlich erkannten Bewegungsrichtung des Clips ab (clip_pool.motion_direction), mit deterministischem Hash-Seed als Fallback. Für push/drift kommt zusätzlich ein dezenter, animierter Keystone/Perspective-Shift für Pseudo-3D-Tiefe dazu.

# ── Zeitdarstellung: rationale Frame-Genauigkeit (nie Float-Drift) ──
class TimeBase(Enum):
    """SMPTE/otio.opentime Standard"""
    SAMPLE_RATE_48000 = (48000, 1)
    FPS_23_976 = (24000, 1001)
    FPS_24 = (24, 1)
    FPS_25 = (25, 1)
    FPS_29_97 = (30000, 1001)
    FPS_30 = (30, 1)
    FPS_59_97 = (60000, 1001)
    FPS_60 = (60, 1)

    @property
    def rate(self) -> Fraction:
        num, denom = self.value
        return Fraction(num, denom)

@dataclass(frozen=True)
class RationalTime:
    """Frame-genaue Zeit, niemals Float"""
    value: Fraction  # z.B. Fraction(24, 1) = 24 frames @ timebase
    timebase: TimeBase
    
    @property
    def seconds(self) -> float:
        """Konvertierung zu Sekunden nur für externe APIs"""
        return float(self.value / self.timebase.rate.numerator * self.timebase.rate.denominator)
    
    def __add__(self, other: 'RationalTime') -> 'RationalTime':
        if self.timebase != other.timebase:
            raise ValueError("Cannot add RationalTimes with different timebases")
        return RationalTime(self.value + other.value, self.timebase)
    
    def __sub__(self, other: 'RationalTime') -> 'RationalTime':
        if self.timebase != other.timebase:
            raise ValueError("Cannot subtract RationalTimes with different timebases")
        return RationalTime(self.value - other.value, self.timebase)

# ── Audio-Features: immutable, die einzige Quelle für Audio-Wahrheit ──
@dataclass(frozen=True)
class BeatGrid:
    """Deterministische Beat-Positionen einer Timeline"""
    timebase: TimeBase
    beats: Tuple[RationalTime, ...]  # sortiert
    
    def next_beat(self, time: RationalTime) -> Optional[RationalTime]:
        return next((b for b in self.beats if b > time), None)
    
    def nearest_beat(self, time: RationalTime, tolerance: RationalTime) -> Optional[RationalTime]:
        candidates = [b for b in self.beats if abs((b - time).value) <= tolerance.value]
        return min(candidates, key=lambda b: abs((b - time).value)) if candidates else None

@dataclass(frozen=True)
class Section:
    """Song-Struktur: Start/End/Label (Intro/Verse/Hook/...)"""
    start: RationalTime
    end: RationalTime
    label: str  # "intro", "verse", "hook", "bridge", "breakdown", "outro"
    
    def duration(self) -> RationalTime:
        return self.end - self.start
    
    def contains(self, time: RationalTime) -> bool:
        return self.start <= time < self.end

@dataclass(frozen=True)
class AudioAnalysisResult:
    """Die EINZIGE kanonische Form von Song-Audio-Eigenschaften"""
    path: str
    bpm: float  # 60..180
    duration: RationalTime
    timebase: TimeBase
    
    # Beat/Struktur
    beatgrid: BeatGrid
    sections: Tuple[Section, ...]
    
    # Energie-Kurve pro Frame
    energy_per_frame: Tuple[float, ...]  # [0..1], len = duration.seconds * fps
    
    # Stimme
    vocal_pitch_hz: float  # Median F0
    mc_gender: str  # "male", "female", "unknown"
    
    # Bewegungs-Features
    repetition_windows: Tuple[Tuple[RationalTime, RationalTime], ...]
    scratch_events: Tuple['ScratchEvent', ...]
    
    # Metadaten für Rendering
    music_dna: Dict[str, Any]  # Beliebiger JSON-Blob aus audio_analysis.py
    
    def section_at(self, time: RationalTime) -> Optional[Section]:
        return next((s for s in self.sections if s.contains(time)), None)
    
    def energy_at(self, time: RationalTime) -> float:
        idx = min(int(time.seconds * len(self.energy_per_frame) / self.duration.seconds),
                  len(self.energy_per_frame) - 1)
        return self.energy_per_frame[idx] if idx >= 0 else 0.0

        return self.end - self.start
    
    def source_duration_needed(self) -> RationalTime:
        """Mit Speed-Ramp: echte benötigte Quellmaterial-Länge"""
        raw = self.duration()
        if abs(self.speed_factor - 1.0) < 1e-3:
            return raw
        return RationalTime(raw.value / Fraction(self.speed_factor), raw.timebase)

@dataclass(frozen=True)
class Timeline:
    """Die KOMPLETTE Schnitt-Entscheidung"""
    song_path: str
    segments: Tuple[TimelineSegment, ...]
    total_duration: RationalTime
    timebase: TimeBase
    
    def validate(self) -> Tuple[bool, List[str]]:
        """Assertions"""
        errors = []
        expected_end = self.segments[0].start if self.segments else self.total_duration
        for seg in self.segments:
            if seg.duration().value <= 0:
                errors.append(f"Segment {seg.index}: duration <= 0")
            if not seg.clip_path:
                errors.append(f"Segment {seg.index}: no clip_path")
        return len(errors) == 0, errors

        timeline_ok, timeline_errors = self.timeline.validate()
        errors = timeline_errors
        if self.resolution[0] <= 0 or self.resolution[1] <= 0:

        if self.crf < 0 or self.crf > 51:
            errors.append("CRF out of range")
        return len(errors) == 0, errors

# gos/core/events.py

@dataclass(frozen=True)
class Event:
    """Basis-Event: Unveränderlich"""
    timestamp: float
    type: str
    payload: Dict[str, Any]

class EventStore:
    def __init__(self, db_path: Path):
        self.db = sqlite3.connect(db_path)
        self.db.execute("""
            CREATE TABLE IF NOT EXISTS events (
                id INTEGER PRIMARY KEY,
                timestamp REAL,
                type TEXT,
                payload TEXT
            )
        """)
    
    def append(self, event: Event) -> int:
        """Fügt ein Event an (nur append, nie update/delete)"""
        self.db.execute(
            "INSERT INTO events (timestamp, type, payload) VALUES (?,?,?)",
            (event.timestamp, event.type, json.dumps(event.payload))
        )
        self.db.commit()
        return self.db.lastrowid
    
    def get_timeline(self, event_type: Optional[str] = None, 
                    after_timestamp: Optional[float] = None) -> List[Event]:
        """Fragt Events ab (nur SELECT, readonly)"""
        query = "SELECT timestamp, type, payload FROM events"
        params = []
        if after_timestamp is not None:
            query += " WHERE timestamp > ?"
            params.append(after_timestamp)
        if event_type:
            query += (" AND" if params else " WHERE") + " type = ?"
            params.append(event_type)
        query += " ORDER BY timestamp"
        
        rows = self.db.execute(query, params)
        return [
            Event(timestamp=row[0], type=row[1], payload=json.loads(row[2]))
            for row in rows
        ]

Engine
Die Entwicklung einer Deep Analysis Engine zur Identifizierung und Optimierung der
viralen Rhythmus-Logik in Kurzvideos erfordert die Schaffung eines komplexen,
integrierten Datenökosystems, das auf einem geschlossenen Regelkreis aus Planung,
Durchführung und Evaluation basiert . Das Kernziel ist es, die subjektive Intuition hinter
dem viralen Erfolg durch ein datengesteuertes System zu ersetzen oder zumindest
signifikant zu unterstützen, indem es die zugrundeliegenden Muster von musikalischen
Strukturen, visuell-rhythmischer Synchronisation und plattformspezifischen Präferenzen
entschlüsselt . Die Architektur dieses Systems ist darauf ausgelegt, lokal im Besitz des
Nutzers zu agieren, was maximale Kontrolle und Flexibilität gewährleistet. Sie stützt sich
auf eine definierte lokale Datenbank, spezifische Render-Warteschlangen und einen
dedizierten Quellordner für Videos und Audiodateien . Diese Infrastruktur bildet die
Grundlage für alle nachfolgenden Analysen und die Generierung optimierter
Inhaltspakete.
Das Fundament des Systems bilden die Pfade zu den Rohmaterialien, die vom Nutzer
initialisiert werden. Dies umfasst mehrere Quellen für Videos (vids_sources), die
Redundanz bieten, um sicherzustellen, dass Material immer verfügbar ist, unabhängig
vom Betriebssystem oder Netzwerkstatus . Für Audiodateien sind separate Pfade
(snd_sources) definiert, die eine klare Trennung zwischen noch zu bearbeitenden
Sounds (snd_todo) und abgeschlossenen, archivierten Titeln (snd_done)
ermöglichen . Dieser strikte Workflow, bei dem Dateien nur umbenannt und nicht
überschrieben werden, stellt sicher, dass keine Historie verloren geht und eine
vollständige Rückverfolgbarkeit erhalten bleibt . Das Herzstück des lokalen Ökosystems
ist die zentrale Datenbank weedit_v4.db, die als Gehirn des Tracers fungiert und alle
Metadaten, Analyseergebnisse und Trainingsdaten speichert .
Die erste Phase der systemischen Umsetzung besteht in der Initialisierung dieser Struktur
durch ein Python-Skript. Dieses Skript überprüft, ob die notwendigen Pfade existieren,
erstellt lokale Arbeitskopien der Standard-Datenbanken (default.clip.db und
default.songs.db), falls keine vorhanden sind, und synchronisiert einen
Trainingspool aus favorisierten HTML-Dateien (FAVs*.html) in einen dedizierten
Ordner (./date/). Diese synchronisierte Datei dient als primärer Input für die Analyse
der bisher erfolgreichsten Clips und bildet das "Gehirn", anhand dessen die Engine lernt,
was als "Feuer" gilt . Die Datenbank selbst wird in zwei Kern-Tabellen strukturiert:
render_queue für die geplante Produktion und viral_feedback für die spätere
Auswertung der tatsächlichen Leistung jedes Clips . Diese zweigleisige Struktur ist
entscheidend für den geschlossenen Regelkreis, da sie eine direkte Verknüpfung zwischen
der vorhergesagten Leistung und der realen Performance herstellt.
Die Funktionalität der Engine wird durch eine Reihe von Skripten und Werkzeugen
gesteuert, die jeweils spezifische Aufgaben übernehmen. Ein zentrales Werkzeug ist der
iTunes-Parser, der die Musikbibliothek des Nutzers scannen und spezielle [BeatSync]
Playlists identifizieren kann . Sobald solche Playlists gefunden werden, werden die darin
enthaltenen Tracks mit den Favoriten aus dem Trainingspool (FAVs.html) kombiniert,
um eine renderbare Warteschlange (render_queue.json) zu erstellen . Dieser Prozess
markiert den Übergang von der reinen Datenaggregation zur aktiven Inhaltserstellung.
Die Analyse der Beats pro Minute (BPM) und der exakten Beat-Times erfolgt dabei nicht
auf Basis der Metadaten aus iTunes, sondern durch eine direkte digitale
Signalverarbeitung mittels des librosa-Bibliotheks in Python . Dies stellt eine
kritische Verbesserung dar, da die BPM-Werte externer Quellen ungenau sein können; die
direkte Analyse des Audiosignals liefert präzise Ergebnisse, die für eine korrekte visuellen
Beat-Syncronisation im Video unerlässlich sind .
Die resultierende Warteschlange ist kein statisches Dokument, sondern eine detaillierte
Anweisung für die Rendering-Engine. Jeder Eintrag enthält Informationen über den
Audio-Track, den Video-Quellclip, die vorhergesagte Viralität und die zu verwendende
Render-Technik . Die Engine berechnet dann die exakten Zeitpunkte für visuelle Effekte,
wie den "Neuro-Trigger", der aus einem Speed-Ramping-Vorgang kurz vor dem Beat und
einem Blitz-Effekt auf dem Beat selbst besteht . Diese Berechnungen werden in
Mikrosegmente zerlegt, die dann einzeln gerendert und schließlich mit FFmpeg
zusammengefügt werden . Die gesamte Prozesskette – von der Scan-Phase über die Beat-
Analyse bis hin zur Segmentierung für das Rendering – wird durch Skripte automatisiert,
was die Effizienz und Reproduzierbarkeit des gesamten Prozesses maximiert.
Zusammenfassend lässt sich die Architektur der Deep Analysis Engine als ein hochgradig
automatisiertes, aber flexibles System beschreiben. Es ist modular aufgebaut, wobei jeder

Die visuell-rhythmische Synchronisation ist der kreative Motor, der die analytischen
Ergebnisse der musikalischen Strukturanalyse in einen fesselnden visuellen Erlebnis
übersetzt . Sie ist der Mechanismus, durch den der Zuschauer aktiv in den Inhalt

Konzentration und potenziell zu einer wiederholten Betrachtung führt . Die Engine zielt

These lautet, dass ein Clip nicht nur auf den Beat geschnitten werden darf, sondern dass
eine gezielte Manipulation von Tempo, Bewegung und visuellen Unterbrechungen das
virale Potenzial maximiert .
Ein zentrales Prinzip der Engine ist die Beat-Synchronisation, die in modernen
Videobearbeitungswerkzeugen wie CapCut und Canva standardmäßig angeboten wird

Kombination aus aufbauender Spannung und abrupter Entladung ist extrem effektiv, um
die Aufmerksamkeit des Zuschauers zu halten, insbesondere in den ersten Sekunden
eines Videos .

Der geschlossene Regelkreis: Automatisierter Feedback-
Mechanismus und Lernprozess
Der entscheidende Unterschied zwischen einem einfachen Editor und einer echten "Deep
Analysis Engine" liegt im geschlossenen Regelkreis, der aus der kontinuierlichen
Erfassung, Analyse und Anwendung von Feedback besteht. Das Projektziel sieht vor, eine
Auto-Optimierungs-Engine zu speisen, die datengetriebene Entscheidungen trifft . Dieser
Prozess wird durch den "Tracer-Scraper" realisiert, der nach dem Upload eines Videos die
harten Metriken von den Plattformen einsammelt und diese als "harte Wahrheit" in die
virale_wahrheit.db zurückfließen lässt . Dieser Mechanismus erlaubt es dem
System, aus Erfolgen und Fehlschlägen zu lernen und seine zukünftigen Vorhersagen und
Produktionsentscheidungen zu verfeinern.
Der Prozess beginnt, sobald ein Clip in die render_queue aufgenommen wird. Nach
dem Rendering und dem Upload an eine oder mehrere Plattformen wartet die Engine
eine definierte Zeitspanne (z.B. 24 Stunden) . Danach startet der Scraping-Prozess.
Dieses Skript greift in die render_queue-Tabelle, identifiziert die Clips, die vor diesem
Zeitpunkt veröffentlicht wurden und noch kein Feedback haben, und initiert einen API-
Aufruf oder einen Web-Scrape auf den jeweiligen Plattformen (TikTok, IG, YT) .
Basierend auf den bereitgestellten Lernmaterialien ist zu beachten, dass APIs oft
Latenzzeiten von bis zu 11 Stunden aufweisen können, was die Planung des Scraping-
Prozesses beeinflussen muss . Die gesammelten Daten, wie Anzahl der Ansichten,
Likes, Teilungen und vor allem die Completion Rate (wie lange die Zuschauer
dranbleiben), werden dann in die viral_feedback-Tabelle geschrieben .
Dieser Schritt ist von fundamentalster Bedeutung, da er eine direkte Verbindung
zwischen der vorhergesagten Leistung (viral_prediction_score) und der
tatsächlichen Leistung herstellt . Wenn ein Clip mit einem hohen Score zwar viele Views,
aber eine niedrige Completion Rate erzielt, deutet dies darauf hin, dass der "Hook" im
ersten Frame nicht stark genug war oder die Schnittfrequenz zu schnell war. Wenn
hingegen ein Clip mit einem moderaten Score eine hohe Replay-Rate hat, könnte dies auf
die erfolgreiche Implementierung eines nahtlosen Loops hindeuten . Der Scraper
speichert nicht nur die Rohzahlen, sondern führt auch eine erste qualitative Analyse
durch, um Gründe für den Erfolg oder Misserfolg zu identifizieren, basierend auf Regeln
wie "Hohe Completion durch perfekten Beat-Sync" oder "Share-Rate deutet auf
Relatability hin" .

# │ 1. RATIONAL TIME (Never Float-Drift)                            │
# └─────────────────────────────────────────────────────────────────┘

class TimeBase(Enum):
    """SMPTE Standard Frame Rates (otio.opentime compatible)"""
    FPS_23_976 = (24000, 1001)    # Film
    FPS_24 = (24, 1)               # Film
    FPS_25 = (25, 1)               # PAL
    FPS_29_97 = (30000, 1001)      # NTSC
    FPS_30 = (30, 1)               # Drop-frame
    FPS_59_97 = (60000, 1001)      # High-speed
    FPS_60 = (60, 1)

    @property
    def rate(self) -> Fraction:
        num, denom = self.value
        return Fraction(num, denom)

@dataclass(frozen=True)
class RationalTime:
    """Frame-exact time, NEVER converts to float internally"""
    value: Fraction          # e.g., Fraction(100, 1) = 100 frames @ timebase
    timebase: TimeBase
    
    @property
    def seconds(self) -> float:
        """ONLY for external APIs (ffmpeg, renderer)"""
        return float(self.value) / float(self.timebase.rate)
    
    def __add__(self, other: 'RationalTime') -> 'RationalTime':
        assert self.timebase == other.timebase, "Timebase mismatch"
        return RationalTime(self.value + other.value, self.timebase)
    
    def __sub__(self, other: 'RationalTime') -> 'RationalTime':
        assert self.timebase == other.timebase, "Timebase mismatch"
        return RationalTime(self.value - other.value, self.timebase)
    
    def __mul__(self, factor: float) -> 'RationalTime':
        """Speed ramping: 0.85x slow-mo, 1.2x speed-up"""
        return RationalTime(Fraction(self.value * factor), self.timebase)

@dataclass(frozen=True)
class BeatGrid:
    """Deterministic Beat Positions"""
    timebase: TimeBase
    beats: Tuple[RationalTime, ...]  # Sorted, immutable
    
    def nearest_beat(self, time: RationalTime, 
                     tolerance: RationalTime) -> Optional[RationalTime]:
        candidates = [b for b in self.beats 
                      if abs((b - time).value) <= tolerance.value]
        return min(candidates, key=lambda b: abs((b - time).value)) if candidates else None

@dataclass(frozen=True)
class Section:
    """Song Structure Segment"""
    start: RationalTime
    end: RationalTime
    label: str  # "intro", "verse", "hook", "drop", "breakdown", "outro"
    
    def contains(self, time: RationalTime) -> bool:
        return self.start <= time < self.end
    
    def duration(self) -> RationalTime:
        return self.end - self.start

        return next((s for s in self.sections if s.contains(time)), None)

        idx = min(int(time.seconds * len(self.energy_per_frame) / self.duration.seconds),
                  len(self.energy_per_frame) - 1)
        return self.energy_per_frame[idx] if idx >= 0 else 0.0

    camera_mode: str                 # "push", "snap", "drift", "hold"
    lighting: str                    # "natural", "lowkey", "highkey"
    color_grade: str                 # "neutral", "warm", "desaturated"
    
    # Effects
    fx: Tuple[str, ...]              # ("grain", "flicker", "chroma")
    transition: str                  # "cut", "push_fade", "scratch", "dissolve"
    
    # Rendering
    speed_factor: float              # <1: slow-mo, >1: speed-up
    
    # Auditing
    confidence: float                # 0..1
    match_reason: str                # "Tag:urban/night | Gender:male | Energy:0.82"
    
    def duration(self) -> RationalTime:
        return self.end - self.start
    
    def source_duration_needed(self) -> RationalTime:
        """CRITICAL: account for speed_factor"""
        if abs(self.speed_factor - 1.0) < 1e-3:
            return self.duration()
        # Speed ramping: need MORE source for slow-mo, LESS for speed-up
        return RationalTime(
            Fraction(self.duration().value / self.speed_factor),
            self.duration().timebase
        )

    segments: Tuple[TimelineSegment, ...]
    total_duration: RationalTime
    timebase: TimeBase

        """Pre-render validation"""
        errors = []
        for i, seg in enumerate(self.segments):
            if seg.duration().value <= 0:
                errors.append(f"Seg {i}: duration=0")
            if not seg.clip_path:
                errors.append(f"Seg {i}: no clip")
            if seg.source_duration_needed() > seg.clip_in:
                # Not enough source material
                errors.append(f"Seg {i}: source too short for speed_factor={seg.speed_factor}")
        return len(errors) == 0, tuple(errors)

        )
        self.db.commit()
        return self.db.lastrowid

        query = "SELECT timestamp, type, payload FROM events"

        return tuple(
            Event(timestamp=row[0], type=row[1], payload=json.loads(row[2]))
            for row in rows

class TracerScraper:
    """Harvests platform metrics → feeds learning engine"""
    
    def __init__(self, db_path: str):
        self.db = sqlite3.connect(db_path)
        self.events = EventStore(db_path)
        self.create_tables()
    
    def create_tables(self):
        self.db.execute("""
            CREATE TABLE IF NOT EXISTS render_queue (
                id INTEGER PRIMARY KEY,
                song_path TEXT,
                output_path TEXT,
                platform TEXT,  -- 'tiktok', 'instagram', 'youtube'
                rendered_at REAL,
                uploaded_at REAL,
                url TEXT
            )
        """)
        self.db.execute("""
            CREATE TABLE IF NOT EXISTS viral_feedback (
                id INTEGER PRIMARY KEY,
                render_id INTEGER,
                platform TEXT,
                views INTEGER,
                likes INTEGER,
                shares INTEGER,
                comments INTEGER,
                completion_rate FLOAT,  -- 0..1
                replay_rate FLOAT,
                scraped_at REAL,
                FOREIGN KEY(render_id) REFERENCES render_queue(id)
            )
        """)
        self.db.commit()
    
    def wait_and_scrape(self, wait_hours: int = 24):
        """Poll every N hours for metrics"""
        query = """
            SELECT id, platform, url FROM render_queue
            WHERE rendered_at < datetime('now', ? hours)
            AND id NOT IN (SELECT render_id FROM viral_feedback)
        """
        renders = self.db.execute(query, (-wait_hours,)).fetchall()
        
        for render_id, platform, url in renders:
            try:
                metrics = self._scrape_platform(platform, url)
                self._record_feedback(render_id, platform, metrics)
            except Exception as e:
                log(f"Scrape failed for {url}: {e}")
    
    def _scrape_platform(self, platform: str, url: str) -> Dict:
        """Platform-specific metric extraction"""
        if platform == "tiktok":
            return self._scrape_tiktok(url)
        elif platform == "instagram":
            return self._scrape_instagram(url)
        elif platform == "youtube":
            return self._scrape_youtube(url)
    
    def _record_feedback(self, render_id: int, platform: str, metrics: Dict):
        """Write metrics → viral_feedback"""
        self.db.execute("""
            INSERT INTO viral_feedback
            (render_id, platform, views, likes, shares, completion_rate, scraped_at)
            VALUES (?, ?, ?, ?, ?, ?, ?)
        """, (
            render_id, platform,
            metrics.get('views', 0),
            metrics.get('likes', 0),
            metrics.get('shares', 0),
            metrics.get('completion_rate', 0.0),
            time.time()
        ))
        self.db.commit()
        
        # Emit event for learning engine
        self.events.append(Event(
            timestamp=time.time(),
            type=EventType.REWARD_RECORDED,
            payload=metrics
        ))

            ORDER BY s.bpm

            JOIN render_queue rq ON vf.render_id = rq.id

def cosine_similarity(vec_a, vec_b) -> Optional[float]:
    """Return None when NO SIGNAL (not 0.0)"""
    if not vec_a or not vec_b:
        return None  # ← KEY: None = "couldn't measure"
    
    n = min(len(vec_a), len(vec_b))
    if n == 0:
        return None  # ← KEY: None = "no common dimensions"
    
    dot = sum(vec_a[i] * vec_b[i] for i in range(n))
    norm_a = math.sqrt(sum(v * v for v in vec_a))
    norm_b = math.sqrt(sum(v * v for v in vec_b))
    
    if norm_a == 0.0 or norm_b == 0.0:
        return None  # ← KEY: None = "orthogonal but measurable"
    
    return max(-1.0, min(1.0, dot / (norm_a * norm_b)))

def execute_isolated_render_job(arguments_list):
    # Spawn the render job in a separate subprocess, freeing system memory on exit

        [sys.executable, "render_worker.py"] + arguments_list,
